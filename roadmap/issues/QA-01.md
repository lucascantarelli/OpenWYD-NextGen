# QA-01 — Recompensa diária nunca chega ao jogador

**Fase:** QA in-game · **Depende de:** issue-35 · **Esforço:** M · **Estado:** ⏳ confirmado na sessão de 05/11

## Objetivo

Um jogador autenticado consegue ver e reivindicar a recompensa diária, e o item aparece no
inventário do personagem no próximo login.

## Contexto / evidência

Medido na sessão de QA de 05/11/2026, com `daily_reward_item` habilitada (item 400, 7 dias):

```
$ psql -c "select count(*) from daily_reward_claim"   → 0
$ psql -c "select count(*) from delivery_queue"       → 0
```

O jogador entrou no cliente (`char login: sending CNFCharacterLogin … name=TestHT`) e **não recebeu
nada** — nem no login, nem por tela alguma.

O motivo é estrutural, não um bug de dados:

- O `tmserver` **não tem nenhum caminho de diária** (`grep daily tmserver/` só acha comentários de
  `delivery_queue`). Ele apenas drena `delivery_queue` (`world/persistence.go`, `ApplyDeliveries`).
- Quem enfileira é `webserver/internal/dailyreward` (`ClaimDailyReward` → `INSERT INTO delivery_queue`),
  com o gate de uma vez por dia em `daily_reward_claim`.
- O serviço `DailyReward` (vitrine + claim) é **player-facing no proto**, mas o portal é BFF de staff
  (`adminCall`, sessão de staff). Não existe superfície em que o jogador clique.

Ou seja: a feature está pela metade — catálogo administrável ✅, claim sem porta de entrada ❌, entrega
no jogo só via fila (que ninguém alimenta).

## Passos

1. Decidir a superfície do claim (rota pública autenticada por conta de jogo, ou grant no login pelo
   `tmserver` chamando o web-api).
2. Se for pelo login: o `tmserver` consulta o claim do dia **off-loop** (como já faz com
   `delivery_queue`) e enfileira/entrega; nunca escreve save direto.
3. Expor a vitrine ao jogador (lista do dia + botão), reaproveitando `ListEnabledDailyRewardItems`.
4. Teste e2e: conta nova → claim → `delivery_queue` tem 1 linha `kind='item' source='daily'` →
   relogin → item no `Carry`.

## Arquivos

- Alterados: `tmserver/internal/world/persistence.go` (ou rota dedicada no `webserver`), `portal/src/app`
  (vitrine), `webserver/internal/dailyreward/`
- Proibido tocar: `internal/store/dailyreward.go` sem necessidade (o gate já está correto)

## Testes / verificação

```bash
docker compose exec -T db psql -U postgres -d postgres -c \
  "select account_id, reward_item_id, claimed_on from daily_reward_claim order by 1 desc limit 3"
docker compose exec -T db psql -U postgres -d postgres -c \
  "select id, kind, status, source from delivery_queue order by id desc limit 3"
```

Saída esperada: uma linha em `daily_reward_claim` para o dia e uma em `delivery_queue` com
`source='daily'`, drenada (`status`) após o login.

## Critérios de aceite

- [ ] Jogador consegue reivindicar a diária do dia por uma superfície jogável.
- [ ] O item aparece no inventário no login seguinte (evidência: `Carry` do personagem + log).
- [ ] Segundo claim no mesmo dia é recusado com mensagem clara.
- [ ] Evidência anexada (SQL antes/depois + log do login).

## Riscos / rollback

- Risco: abrir rota pública sem autenticação de conta de jogo → vazamento de item. Mitigação: claim
  sempre derivado do `account_id` da sessão, nunca do corpo.
- Rollback: desabilitar a linha em `daily_reward_item` (`enabled=false`) para o efeito parar sem deploy.
