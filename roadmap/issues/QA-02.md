# QA-02 — Overlay de stat apaga aparência, clã e equipamento do mob

**Fase:** QA in-game · **Depende de:** issue-34 · **Esforço:** M · **Estado:** ⏳ confirmado na sessão de 05/11

## Objetivo

Editar **um** campo de stat de um template (ex.: `exp`) sem destruir os outros: aparência, clã e
equipamento do mob continuam os do template original.

## Contexto / evidência

Na preparação do roteiro de sessão única foi criada uma linha mínima em `mob_template_stat`
(`Troll`, `level=1`, `exp=250000`, `max_hp=120`) e nenhuma em `mob_template_equip`. O boot registrou:

```
msg="mob template stat overlay enabled (moderator editing)" overrides=1
```

No cliente, o mob apareceu **com o modelo base de TK** e **não era possível atacá-lo**. A causa está
em `tmserver/internal/mobstat/mobstat.go`, que trata o formulário como autoritativo em todos os campos:

```go
mob.Clan = ov.Clan
mob.Merchant = ov.Merchant
mob.Class = ov.Class
...
mob.Equip = [savefmt.MaxEquip]savefmt.Item{}   // slots não listados são limpos
```

Como as colunas de `mob_template_stat` são `NOT NULL DEFAULT 0`, uma linha que só quer mexer em EXP
também grava `class=0`, `clan=0` e zera o `Equip` — o mob perde modelo e arma. Pior: em
`world/city.go`, `nonCombatNPC(merchant, clan, x, y)` devolve `true` quando `clan == 0` dentro de uma
aldeia (`!ClanHostile(0, 0)`), então o mob vira **NPC de serviço**: não ataca e não pode ser atacado.
Os dois sintomas do teste ("skin do TK" e "impossível de atacar") têm a mesma raiz.

Correção aplicada na hora (workaround, não é a correção): `mob_template_stat` do `Troll` foi apagada e
o `tmserver` reiniciado com `overrides=0`, restaurando o template original.

## Passos

1. Introduzir semântica de "herdar do template": colunas anuláveis (ou flag `inherit_<campo>`) para
   `class`, `clan`, `merchant` e `equip`, aplicadas só quando informadas.
2. Enquanto a coluna nula não existir, o upsert do web-api deve **copiar** o valor atual do template
   para o formulário (o portal já lê o blob pelo catálogo) em vez de gravar `0`.
3. Teste de regressão em `tmserver/internal/mobstat`: aplicar override só de `exp` num blob real e
   comparar byte a byte que `Clan`, `Class` e `Equip` não mudaram.
4. Revalidar no cliente: mob com override de EXP mantém modelo, arma e comportamento hostil.

## Arquivos

- Alterados: `tmserver/internal/mobstat/mobstat.go`, `tmserver/internal/mobstat/mobstat_test.go`,
  `internal/store/` (upsert do catálogo), `portal/src/app/(admin)/mobs/`
- Proibido tocar: `Release/` (o template é do banco, `npc_template`)

## Testes / verificação

```bash
go test ./tmserver/internal/mobstat/ -run TestApply -v
```

Saída esperada: caso novo `TestApplyExpOnlyKeepsIdentity` verde, comparando `Clan`, `Class` e
`Equip` antes/depois.

## Critérios de aceite

- [ ] Override de um único campo não altera os demais (teste byte a byte).
- [ ] Editar EXP/HP no portal mantém a aparência e o comportamento hostil do mob no cliente.
- [ ] `mob_template_equip` vazio não zera o equipamento do template.
- [ ] Evidência anexada (teste + captura/log do mob com override).

## Riscos / rollback

- Risco: mudar a semântica de "equip autoritativo" quebrar o caso de "limpar equipamento de propósito".
  Mitigação: `equip` explícito vazio continua limpando; o que muda é o *default* (herdar).
- Rollback: apagar a linha em `mob_template_stat` e reiniciar o `tmserver` (overlay é boot-only).
